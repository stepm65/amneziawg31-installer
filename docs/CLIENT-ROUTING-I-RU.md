# Клиенты AWG 3.1: опциональные I1–I5 и дополнительные IPv4-маршруты

Эта возможность добавлена в **v0.5.1-test**. Перед эксплуатацией на сервере сделайте snapshot VPS и протестируйте связь на одном временном клиенте. Kernel/DKMS и существующие интерфейсы `awgN` при обновлении приложения не переустанавливаются.

## I1–I5: включить / выключить

В **Клиенты → Конфигурация → Маршруты и имитация трафика** доступен переключатель `Использовать I1–I5 для этого клиента`.

- По умолчанию `off`, т. е. поля `I1`–`I5` **не попадают в экспортируемый конфиг**.
- Если включено, **необходимо** заполнить `I1`; `I2`–`I5` можно оставить пустыми.
- Пример допустимого `I1`: `<r 48>`; можно использовать `<t>` и `<b 0xaabbcc>` и поддерживаемые теги `<rc N>`, `<rd N>`; форматы проверяются и общий объём ограничивается.
- Значения находятся **в секции `[Interface]` клиента**, не в серверном `[Interface]`.
- Изменения `I1–I5` **не требуют перезапуска серверного интерфейса**, но требуют повторного импорта клиентской конфигурации.
- QR содержит те же значения, что `.conf`. Некоторые приложения и QR-сканеры могут не импортировать большой или неподдерживаемый профиль. Используйте `.conf` при таких проблемах; не удаляйте необходимые параметры ради QR.

`I1–I5` — пакеты имитации протокола на инициирующей стороне, а не флаги версий AWG. Не все клиенты понимают все теги. Прежде чем отправить на Android/iOS/Windows, проверьте поддержку выбранных тегов в установленной версии клиента.

## Подсети или отдельные адреса **за** клиентом

Пример: сервер `awg0` в `10.77.10.0/24`, клиент-роутер `10.77.10.2/32` с локальной сетью `192.168.50.0/24` и отдельным хостом `172.20.10.5`.

В форме клиента укажите:

```text
192.168.50.0/24
172.20.10.5
```

Адрес без маски преобразуется в `/32`. Серверный `[Peer]` будет содержать:

```ini
AllowedIPs = 10.77.10.2/32, 192.168.50.0/24, 172.20.10.5/32
```

**Конфигурация этого клиента не получает автоматически эти LAN-подсети в `[Peer] AllowedIPs`:** его маршрут исходящего трафика остаётся `0.0.0.0/0` (режим Full Tunnel) либо VPN-сеть (Split Tunnel). Это разные направления маршрутизации.

Контроллер добавляет/удаляет маршруты Linux для подсетей за активными клиентами и разрешающие правила FORWARD для трафика между VPN-клиентами и указанными подсетями. Правила ограничены соответствующими префиксами и интерфейсом AWG. При старте `awg-quick` маршруты создаются из серверного `AllowedIPs` и правила поднимаются через `PostUp`.

### Обязательные настройки на стороне клиентского роутера

На клиентском устройстве, за которым находится LAN:

1. Включите `net.ipv4.ip_forward=1` (если это Linux-роутер).
2. Разрешите нужный FORWARD между VPN-интерфейсом клиента и LAN в его firewall.
3. Убедитесь, что хосты LAN возвращают трафик через этот роутер (или настройте маршруты/точечный NAT на стороне клиента самостоятельно).
4. Если нужны LAN→интернет через VPN-сервер, это отдельный сценарий: текущая версия **не** включает NAT для дополнительных LAN-подсетей автоматически.

### Защита маршрутов

- Только IPv4. Маски `/8.. /32`, без default route.
- Не допускаются пересечения с VPN-подсетью, маршрутами других клиентов, другими AWG-интерфейсами и уже имеющимися маршрутами VPS.
- До 16 сетей на клиенте; при неверной конфигурации операция отклоняется.
- Перед изменением профиля сохраняется root-only резервная копия в `/var/backups/awg31-panel/peers/`.
- Существующий `awg0` не пересоздаётся и не требует перезапуска при обычном изменении peer AllowedIPs.

## Проверки после обновления

```bash
sudo /usr/local/sbin/awg31mgr servers
sudo awg show awg0
ip -4 route show dev awg0
sudo iptables -S FORWARD | grep awg0
sudo systemctl status awg31-panel --no-pager
```

Протестируйте на LAN-хосте и с другого VPN-клиента доступ к новому IP, затем удаление маршрута и повторную проверку. Перед тестом на публичном сервере рекомендуется создать snapshot VPS.
